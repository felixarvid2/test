# Quick design (thor-survivors)

Adapted from Claude-Code-Game-Studios (MIT), see .claude/CCGS-LICENSE.txt.

Output is one spec the `implementer` can build from without asking anything. No design documents exist in this repo;
the spec lives in the reply (or in the PR description), not in a new folder. Vampire Survivors is the reference.

## Steps

1. Classify: **Tuning** (only numbers in `game_data.json`: give a table old -> new and the measurement that
   justifies it, see `thor-survivors-balance`), **Tweak** (change to an existing behaviour), **Addition** (new weapon,
   enemy, passive, pickup, stage mechanic, shop item). Tuning needs no more than the table plus acceptance criteria.
2. Read before writing (via `Explore`): the closest existing thing and how it is wired. Where things live:
   - Data: `thor-survivors/app/src/main/assets/game_data.json` is generated by `tools/build_data.py` from REA
     (`python3 tools/build_data.py /path/to/REA/data`). A new thing the REA data lacks needs an extension in the
     generator or a documented post-step, otherwise regenerating erases it. State which.
   - Weapon: `behaviorOf(key)` in `game/Sim.java` maps weapon keys (and their evolutions) to behaviour ids; each has a
     `P_*` projectile kind in `game/Entities.java`; `Inventory`/`OfferGenerator` handle slots, level-up offers and
     evolution (`evoInto`, `evoSynergy`); card text in `game/Describe.java`.
   - Enemy: `data/EnemyDef`, wave rows in `stages.<KEY>.rows`, procedural look in `game/EnemyType.java`, sprite
     mapping in `tools/build_atlas.py` (skill `thor-survivors-sprites`).
   - Passive / stats: `game/PlayerStats.java`; shop: `powerups` plus `game/MetaProgress.java`.
   - Visuals: `render/WorldRenderer.java` (world, effects `FX_*`), `ui/PanelRenderer.java` (bottom screen).
   - Sound: ids are `game/SoundEvents.java` (`NAMES`, `MAX_PER_WINDOW`, `MIN_GAP`, `VOICES`), files
     `app/src/main/assets/audio/sfx/<id>.ogg` and `manifest.json`, built by `tools/import_audio.py`, spec
     `tools/AUDIO_SPEC.md`; `AudioManifestTest` and `SoundEventsTest` pin the id list, so a new id means updating them.
3. Draft the spec (below). Prefer reusing an existing behaviour with different data over a new code path. State the
   pool and cost impact: entities must come from the fixed pools (`Sim.MAX_PROJ` etc.), nothing allocated per frame.
4. Challenge it as `game-designer` would: what does it replace, which build does it make dominant, what is the stage
   minute where it matters, and is it fun without the other new things. Flag risks instead of hiding them.

## Spec template

```
# <Title>   Type: Tuning | Tweak | Addition
Why: one sentence, the player problem or fantasy (cite the owner's feedback if any).
Data: game_data.json keys and values per level (table), plus what regenerates them.
Behaviour (Sim): exact rules, formulas with units (ms, world units, per second), edge cases: no target, pool full,
  crit, knockback, 60 vs 120 Hz (dt-scaled), evolution and its passive.
Visuals: sprite source or procedural drawing, effect kind, readability on the 560-unit-high view.
Sound: existing event id or a new one (name, line in AUDIO_SPEC.md, limiter values).
Text: level-up card line (Describe), README line to update (Swedish).
Tests: named JVM tests (SimSmokeTest/WeaponBehaviourTest style, seeded, stationary dummies) with the expected numbers;
  screenshot if visual (skill thor-survivors-screenshots).
Acceptance: binary checks, e.g. "level 3 deals 1.5x level 1 damage per hit", "never more than 12 live projectiles".
Out of scope: ...
Open questions for the owner (max 2).
```
Hand the finished spec to `implementer` (or `mechanic` when it is only data values). Ship with
`thor-survivors-release`.
